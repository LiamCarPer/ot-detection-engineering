# Performance and reliability

This page records three measurements and the limits of each:

1. **Decoder microbenchmark** — how fast the Rust DNP3, S7comm and OPC UA
   decoders process the committed example frames. The Modbus decoder is covered
   by its own tests and the decoder-to-rule proof, but is not in this
   microbenchmark yet.
2. **Offline replay** — how fast the validation matcher processes benign events
   through every single-event Sigma rule.

The committed evidence is `deploy/evidence/perf/summary.json`, generated by
`python tools/perf_check.py` and guarded by `make perf-check`.

## What was measured

| Field | Value |
| :-- | :-- |
| Host | AMD Ryzen 5 3400G, 8 CPUs, 30 GB RAM |
| Platform | Linux x86_64, kernel 6.18 |
| Toolchain | Rust / cargo 1.98.0, Python 3.12.3 |
| Decoder iterations | 10,000, after 100 warm-up iterations |
| Replay | 1,000 distinct benign events × 10 repetitions (10,000 evaluation passes) through 30 single-event Sigma rules |
| Build | `--release`, workspace LTO and `codegen-units = 1`, overflow checks on |

## Decoder results

| Protocol | Frames per iteration | Throughput | p50 / frame | p99 / frame | Peak RSS |
| :-- | --: | --: | --: | --: | --: |
| DNP3 | 4 | ~7.8M frames/s | 90 ns | 190 ns | ~2.4 MB |
| S7comm | 4 | ~11.0M frames/s | 50 ns | 60 ns | ~2.4 MB |
| OPC UA | 5 | ~8.5M frames/s | 80 ns | 100 ns | ~2.5 MB |

The example frames are deliberately small: a DNP3 link frame, an S7 TPKT/COTP
PDU, an OPC UA header. The benchmark measures **decoder overhead**, not a full
packet-capture pipeline. It does not include libpcap, TCP reassembly, JSON
serialization to Loki, or the SIEM.

## Offline replay results

| Metric | Value |
| :-- | --: |
| Events | 10,000 evaluation passes over 1,000 distinct events |
| Rules per event | 30 |
| Throughput | ~2,800 events/s |
| p50 / event | ~264 µs |
| p99 / event | ~1,501 µs |
| Matches on benign events | 0 |

This measures the Python validation matcher, not the production path. It is a
useful budget for the test harness and for comparing rule changes; it is not a
claim about a production sensor.

## SLOs

| SLO | Target | Result |
| :-- | :-- | :-- |
| Decoder p99 per frame | ≤ 10 µs | pass (all protocols) |
| Offline replay throughput | ≥ 1,000 events/s | pass (~2,800) |
| Benign replay matches | 0 | pass (0) |

The SLOs are intentionally loose. They catch a pathological regression, not a
small run-to-run variation. `make perf-check` recomputes each pass/fail from the
recorded numbers; a stored boolean cannot make a bad number pass. The numbers
themselves are hardware-specific.

## Reproduce

```bash
make perf          # run the benchmark and rewrite deploy/evidence/perf/summary.json
make perf-check    # validate the committed evidence structure (fast)
```

`make perf` requires cargo and takes a few seconds for the release build. It is
not part of `make check`; the evidence is committed and validated by
recomputing the SLOs from the recorded numbers.

## What this does not prove

- **Not a production throughput benchmark.** The host is a desktop, the frames
  are small, and there is no network I/O.
- **No packet-capture replay.** The benchmark calls the decoders directly; it
  does not run libpcap or a full TCP reassembly path.
- **No production backpressure or PCAP sensor replay.** The bounded-queue
  matcher load section covers a slow consumer and a full queue at 20,000 EPS;
  a real sensor replay and a sensor restart are still untested.
- **No SIEM cost measurement.** Loki/OpenSearch storage and query cost are not
  measured here.
- **Numbers vary.** The committed run is one sample; the hardware and method are
  recorded so a different host can be compared honestly.

## Sustained matcher load

The decoder microbenchmark is not a load test. This run replays the normalized
events from the 9.5-minute lab-benign pilot at a fixed arrival rate through
every single-event Sigma rule, with a bounded queue.

| Target | Achieved | Drops | p99 | Max queue |
| ---: | ---: | ---: | ---: | ---: |
| 4,000 events/s | **~3,512 events/s achieved** | 0 | ~0.97 s | 3,625 |
| 20,000 events/s | ~3,036 events/s | ~75,161 (75.2%) | ~3.7 s | 10,000 |

At a 4,000 EPS target the producer achieves ~3,512 EPS with no drops; the
Python producer loop, not the bounded queue, is the limit at this rate. At
20,000 EPS the consumer saturates, the queue fills, and the producer drops
~75.2% rather than growing without bound. This is a single-process Python
matcher on the real Modbus+flow corpus, not a production sensor or a pcap
replay.

The event file is produced from a capture:

```bash
python tools/benign_lab_check.py --pcap <lab.pcap> --events-out /tmp/benign-events.jsonl
make load-check LOAD_EVENTS=/tmp/benign-events.jsonl
```
